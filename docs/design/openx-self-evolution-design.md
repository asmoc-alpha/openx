# OpenX 自演进设计方案 · 演进即重组，证据即门槛

> 定位：本文集合三份既有设计稿，回答一个问题——**openx 如何成为一个可以
> 自演进的 agent**。
>
> 上位文档：
> - `docs/openx-architecture-design.md`（v4.1 总架构）——会消融的 harness、
>   六条标准、模型能力档案、双棘轮、脚手架退场、"演进即重组"；
> - `docs/openx-kernel-design.md`（v2.1 内核详设）——四职责闭环、Guard
>   半格、晋升门 admit()、双账本与决策留痕；
> - `docs/design/microkernel-design.md`（五件套）——模型驱动装配元工具、
>   Manifest 自描述、协议分类、故障隔离、§6 模型自产插件（自举引擎）。
>
> 三份稿子各自给出了自演进的**零件**：本文把它们装配成一个闭环，并补齐
> 闭环上尚未设计的环节（缺口感知、评测门、经验沉淀、装配策略学习）。
> 机制变更须先改本文再改代码。

一句话：**自演进 = 组合输入的受控突变——模型提出变更，沙箱出证据，
晋升门做审批，账本留全痕，评测定去留；内核永不在演进对象之列。**

---

## 0. 什么算"自演进"

### 0.1 定义

agent 在运行中改变自己的能力面、策略或组合，且每次改变同时满足三条：

1. **有证据**——变更前经沙箱自测或退场评测，信任锚点是"跑绿了 /
   不掉点"，不是"模型说它能用"；
2. **有审批**——变更过晋升门（只读纯加法可热插，写类/常驻须用户确认），
   模型只配对、内核才定位、用户是终审；
3. **有痕迹**——变更即决策事件上账本，可归因（谁提的、谁批的、依据
   什么）、可回滚（回滚 = 卸载，一键逆操作）。

三条缺一条，就不叫自演进，叫失控。

### 0.2 三个"不等于"

| 不等于 | 依据 |
|---|---|
| ≠ 模型修改内核 | 不变量 #7：TCB 对动态插入关闭。棘轮、评测门、晋升门、账本格式本身永不进演进对象——否则模型可以"先卸载记录仪再作案" |
| ≠ 无门的自我改写 | 一切变更走 admit() 同源同门：与 boot 装配共用同一五阶段校验，无第二条加载路径 |
| ≠ 一次性配置 | 自演进是持续闭环：感知 → 生成 → 验证 → 审批 → 灰度 → 评测，环上的产物（轨迹、账本）回流为下一轮演进的输入 |

### 0.3 演进对象四分

| 层 | 演进对象 | 对应机制 | 现状 |
|---|---|---|---|
| 能力层 | 插件（自产 auto-* / 第三方 / 用户）、MCP、skills | 候选池 → 模型配对 → 晋升门 → 热插 | P-A/P-B/P-C/P-F 已落地 |
| 策略层 | 装配策略（哪类任务装哪些插件）、prompt 片段、上下文预算、记忆写入 | 上下文协议（context/v1）+ overlay 补丁 + 轨迹分析 | context/v1 已落地；策略学习待 E5 |
| 脚手架层 | loop / 压缩 / 路由 / 子代理 / 记忆检索 | compensates + exit_when 声明 + 退场评测门 | 声明待 E1，评测门待 E4 |
| 组合层 | 模型能力档案、用户/项目 overlay | base bundle = f(档案)，overlay 补丁原语 | P6 待落地 |

**TCB（内核五件套 + 七项不变量）不在任何一层。** 演进全部表现为"改
组合输入"，内核零改动——这是 v4.1 §10.3"演进即重组"的完整含义。

### 0.4 业界参照与 openx 对应物

设计一个可自演进的 agent，文献与业界实践中反复出现四种模式；openx
对每一种都有机制落点，且多了一层它们普遍缺失的东西——**门与账**：

| 模式 | 代表 | openx 对应物 | openx 多出的一层 |
|---|---|---|---|
| 技能库积累 | Voyager：代码即技能，入库复用 | 自产插件（auto-*）+ 插件目录（list_plugins 摘要索引）供后续任务配对复用 | 晋升门：技能入库须用户审批；批量回滚 |
| 经验反思 | Reflexion：失败 → 文字经验 → 下轮回喂 | 会话账本 → 记忆（memory / coding_memory）→ context/v1 召回 | 经验写入也记账；召回走协议不硬编码 |
| 自改代码 + 评测门 | Darwin-Gödel Machine：自修改必须过基准回归 | 退场评测门（摘除后成功率不掉点才准退场）+ self_test 沙箱 | 评测门与棘轮对模型关闭，不可自我豁免 |
| 元学习装配 | 按任务学"该装哪些模块" | 装配策略学习（轨迹 → 配对建议 → overlay） | 建议永远只是候选，定位权在内核 |

openx 的独特立场：**别家把自演进做成"模型自己的能力"，openx 把自演进
做成"内核治理下的受控过程"**——模型是演进的发起者与执行者，但门槛、
证据、终审、留痕全在不被替换者手里。模型越自主，门与账越要重（v4.1
§7.3：变重的只有账本与把关）。

## 1. 总框架：一个闭环，三条主线

### 1.1 自演进闭环（六环）

```
        ┌────────────────────────────────────────────────┐
        │              账本 / 轨迹（证据底座）              │
        ▼                                                │
  ① 感知缺口  →  ② 生成候选  →  ③ 沙箱验证  →  ④ 晋升门  →  ⑤ 灰度激活
                                                            │
        ┌────────────────────────────────────────────────┘
        ▼
  ⑥ 评测与退场 ──(掉点/退化)──→ 回滚 = 卸载 ──→ 回到 ①
```

每一环都有既有机制承接，无一环需要发明新权力：

| 环 | 做什么 | 承接机制 | 状态 |
|---|---|---|---|
| ① 感知缺口 | 识别"缺什么能力 / 什么在拖后腿" | 账本+轨迹中的失败模式；任务失败；用户显式要求 | **待 E3**（现为隐式：模型会话内自知） |
| ② 生成候选 | 产出插件 / 补丁 / 退场建议 | PluginSpec 契约 + write_plugin 结构化输出；模型配对产"候选+建议位置" | 已落地（P-F） |
| ③ 沙箱验证 | 出证据：self_test 跑绿 | admit 管线③：daemon 线程自测 + 10s join 超时即拒；调用防护（timeout/熔断/输出上限） | 已落地（P-C/P-F） |
| ④ 晋升门 | 审批：只读热插 / 写类用户确认 | admit()：形状校验 → 静态扫描 → 自测 → 会话热插 → 用户晋升 | 已落地；K6 以 MCP 为 pilot |
| ⑤ 灰度激活 | 先 session 后 persistent | 注册作用域：session（不进下次 boot）→ 晋升（写回组合） | 已落地（session）；persistent 写回组合待 P6 |
| ⑥ 评测与退场 | 证据决定去留：退场评测门 | 脚手架声明 compensates/exit_when + 评测回归 + 决策记账 | **待 E1/E4** |

### 1.2 三条演进主线

闭环按对象不同跑出三条线，共享同一套门与账：

```
增生线  能力缺口 → 自产插件(auto-*) → 自测 → 晋升 → 能力库沉淀 → 复用配对
消融线  档案升级 → 脚手架 exit_when 命中 → 退场评测门 → 摘除(非删除) → 降级回挂
调优线  轨迹汇聚 → 离线分析 → 装配/上下文/记忆策略建议 → overlay 过门 → 生效灰度
```

- **增生线**让 agent **长**——补能力短板（microkernel §6 自举引擎）；
- **消融线**让 agent **瘦**——模型变强后脚手架有序退场（v4.1 §10）；
- **调优线**让 agent **准**——同样的能力面，装配与上下文策略越用越合手
  （microkernel §1.2/§6.6 Tracer-eval 闭环）。

三条线的方向相反相成：增生防"做不到"，消融防"带病死"，调优防"会用但
用不好"。**净效果 = harness 随模型进步而变薄，能力面随使用积累而变厚。**

## 2. 主线一：能力增生（自产插件）

### 2.1 缺口感知：候选从哪来

| 来源 | 信号 | 形态 |
|---|---|---|
| 任务内显式缺口 | "没有趁手的工具"——模型在会话中直接识别 | 当会话 write_plugin，立竿见影 |
| 失败模式复现 | 同类任务反复绕路（轨迹中反复出现的笨路径） | E3：离线从账本聚类出"缺口报告"，下次会话作为上下文片段提示 |
| 用户显式要求 | "把这个流程做成命令/工具" | 当会话生成 + 晋升，跨会话沉淀 |
| 配对策略反馈 | 某类任务预装清单命中率低 | E5：装配策略学习，反过来提示缺哪类插件 |

原则：**缺口可以来自模型的自知，但证据与审批永远不来自模型。**

### 2.2 生成与验证（已落地，P-F）

```
write_plugin(manifest, code, test)     ← 结构化输出，schema 即契约
  → ① 形状校验   manifest 齐全、permissions 在词汇表内、auto-* 前缀
  → ② 静态扫描   AST：声明权限 vs 实际调用、命名空间越界
  → ③ 沙箱自测   daemon 线程跑 self_test，10s 挂死即拒    ← 信任锚点
  → ④ 会话热插   scope=session，立即可用
  → ⑤ 用户晋升   写类/常驻 → 用户确认 → persistent + plugin_promoted 记账
```

全程同源同门：生成文件落进插件目录后就是普通插件，走同一五阶段校验，
可被 list / unload / 回滚一视同仁——无第二条加载路径。

### 2.3 能力库沉淀：从"一次性补丁"到"可复用技能"

自产插件若只服务当前任务，价值止于当会话；自演进的关键一跃是**沉淀为
能力库，供未来任务配对复用**：

1. **目录即索引**：`list_plugins` 暴露一句话摘要 + token 成本（不进
   schema），是未来会话的第一认知入口——auto-* 插件与用户/第三方插件
   同池同门；
2. **摘要质量即复用率**：write_plugin 的 manifest.summary 是配对的唯一
   依据，生成侧应把"什么任务该装我"写进摘要——这是模型写给未来自己的
   检索键；
3. **存活率即质量信号**：自产插件的后续被装配率、被卸载率、熔断率全在
   轨迹里——"哪些自产插件真有用"有统一数据源（microkernel §6.6），
   低质量 auto-* 可被整体盘点、批量回滚。

### 2.4 增生的安全边界（承接 microkernel §6.5，不重述机制只列立场）

- 生成插件恒 `trust=auto` 独立一档——可批量回滚、可整体禁用，不并入
  user；
- ToolHost 拒绝面不变：自产插件同样拿不到 agent 本体（loop/闸门/console）；
- prompt injection 的最坏结果 = 推荐错插件或写出一个沙箱里的坏工具，
  不能发明注册位置，不能触碰棘轮与门。

## 3. 主线二：脚手架消融（退场）

### 3.1 声明先行：每个脚手架必须自带讣告

v4.1 标准三：每个脚手架声明 `compensates` 与 `exit_when`。落地形态 =
声明进 manifest（E1）：

```yaml
# 例：历史压缩插件的演进声明
scaffold:
  compensates: "模型上下文有限"
  exit_when: "长会话免压缩评测通过（任务成功率不掉点）"
  eval_set: "evals/long-session.jsonl"      # 退场评测的任务集
  fallback: "reinstall-on-regression"       # 模型降级时自动回挂
```

答不出 compensates 与 exit_when 的模块，按标准三没有资格以脚手架身份
存在——要么进内核（TCB，永不演进），要么降级为普通能力插件。

### 3.2 退场三步（v4.1 §10.2，落为可执行流程）

```
① 评测门   在 eval_set 上对比"带脚手架 vs 摘除"的任务成功率
           不掉点 → 准许；掉点 → 保持，记录本次评测证据
② 决策记账 scaffold_retired 事件上全局账本：谁发起、评测数据、审批人
③ 摘除     从动态 base 组合输入删一行——摘除不是删除，代码与注册仍在，
           只是不再进应载清单；模型降级（档案回退）时自动回挂
           （scaffold_restored，同样记账）
```

消融线的方向与安全棘轮正交：能力棘轮**双向**（跟模型实测进退），安全
棘轮**单向**（只紧不松）——脚手架退得再多，Guard 与资源闸一寸不让。

### 3.3 与能力档案联动

消融的触发源不是时间，是**档案变化**：模型升级 → 能力档案更新 →
exit_when 条件命中 → 发起退场评测。换模型 / 模型升级 = 改 Provider
实现 + 档案，组合自动重算，内核零改动（v4.1 标准五）。回挂同理：
模型降级 → 档案回退 → 已摘除脚手架自动回到应载清单——**能力棘轮的双向
性由"组合是档案的纯函数"结构性保证**，不靠运维记性。

## 4. 主线三：策略调优（轨迹 → 经验 → 装配）

### 4.1 数据基座：账本即语料

调优线消费的不是新数据，是记账职责的既有产出（kernel 详设 §3）：

| 数据 | 来源 | 调优用途 |
|---|---|---|
| 转录事件（tool_use/result、cause 链） | 会话账本 | 失败模式聚类、笨路径识别 |
| 裁决事件（permission_decision 逐站 trace） | 会话账本 | 权限摩擦点分析（哪些 ASK 该沉淀为规则） |
| 装配事件（load/unload/promote/熔断） | 会话账本 | 装配策略：哪类任务预装哪些插件 |
| 成本字段（token/时长/费用） | 轨迹（P-E 待补） | 上下文预算分配、压缩收益核算 |
| 决策事件（promoted/retired/rolled_back） | 全局账本 | 演进历史审计、回滚率统计 |

**P-E 轨迹升级是调优线的前置**：账本补成本字段 + eval 导出——"发生过
什么"与"为什么这么设计"共用同一数据源（microkernel §0.2 ④）。

### 4.2 学四样东西

| 学什么 | 信号 | 动作 | 门 |
|---|---|---|---|
| 装配策略 | 任务类型 × 插件装配 × 成败 | "这类任务预装这些插件"的配对建议 | 建议进 overlay，过晋升门生效 |
| 上下文预算 | 各 context 插件片段长度 × 命中率 | 调整征集优先级与字符预算 | 同上 |
| 记忆质量 | 记忆召回后是否真的被用 | 记忆写入/修剪策略 | 同上 |
| 权限规则 | 重复 ASK 且恒被批准的模式 | 建议沉淀为存储规则 | 用户裁决（现状 ALLOW_SESSION 语义） |

### 4.3 先离线，后在线

- **第一步（E5，离线）**：分析报告——人从轨迹读"缺口报告 / 装配命中
  率 / 权限摩擦点"，手动改 overlay。人闭环，系统只出证据；
- **第二步（远期，在线）**：模型自己读自己的轨迹摘要，产出 overlay
  补丁建议——但补丁仍过晋升门，用户终审。**在线化只改建议的发起者，
  不改门的位置。**

### 4.4 经验沉淀：会话 → 记忆 → 召回

单会话内的"学会了"要跨会话存活，路径是：

```
会话账本（事件流）
  → 会话收尾：提炼经验（成功的路径、失败的教训、项目约定）
  → 写入记忆（memory / coding_memory，将来收口为 memory_backends 注册项）
  → 未来会话：context/v1 征集片段并入系统提示（注册序 + 字符预算）
  → 召回质量回流轨迹（被召回的记忆是否被实际使用）
```

这是 Reflexion 模式的 openx 形态，差别在：经验写入与召回都走注册项与
协议，不硬编码进 loop；记忆后端是可换槽位，不是内核私有物。

## 5. 治理：双棘轮 + 信任分级 + 审批矩阵

### 5.1 审批矩阵（演进变更 × 信任级）

| 变更类型 | builtin | third-party | user | **auto（模型自产）** |
|---|---|---|---|---|
| 只读插件热插（observe） | 校验过即插 | 校验 + 一次性确认 | 校验过即插 | 校验 + self_test 过即插（session） |
| 写类插件 / hooks（act） | 不可能（内置无动态插入） | 用户确认 + session 灰度 | 用户确认 | self_test + **用户确认** + session 灰度 |
| 晋升 persistent | — | 用户确认 + 记账 | 用户确认 + 记账 | 用户确认 + 记账（plugin_promoted） |
| overlay / 策略补丁 | — | — | 用户操作即授权 | **永远只是建议**，用户终审 |
| 脚手架退场 | 评测门 + 用户确认 + 记账 | — | — | 模型可发起评测，**摘除须用户确认** |
| 棘轮 / 评测门 / 门本身 | **对一切动态插入关闭（TCB）** | — | — | — |

auto 列的两条铁律：**自测是放行的前提，不是放行的替代**（self_test
绿了仍须用户晋升写类插件）；**auto-* 一键批量回滚恒可用**（命名空间
三律之三）。

### 5.2 回滚体系

| 粒度 | 操作 | 依据 |
|---|---|---|
| 单插件 | unload = 回滚（注册即记账的逆操作） | 账本答"什么时候来的、谁装的" |
| 命名空间 | auto-* 整体回滚 | 同源同门落点：一眼识别、一键撤出 |
| 组合 | overlay 撤销补丁 → 下次 boot 复原 | 组合决议记账（composition_resolved） |
| 脚手架 | 摘除可恢复（摘除不是删除） | scaffold_restored 决策事件 |

### 5.3 反注入立场

模型在闭环里是**发起者**不是**裁决者**：配对建议的合法域 = 插件注册
目录（内核枚举），目录外一律拒；自产代码过 AST 静态扫描 + 沙箱自测；
一切写类变更有人审。注入最坏结果收敛为"推荐错插件 / 沙箱里一个坏
工具"——进不了门，碰不了账，动不了棘轮。

## 6. 证据底座与度量

### 6.1 对既有记账职责的增量要求

记账四职责不变，自演进只加三类消费：

1. **eval 导出**（P-E）：账本 → 评测任务集与对照数据——退场评测门的
   输入；
2. **成本字段**（P-E）：每条装配/调用事件附 token/时长/费用——调优线
   的量化基础；
3. **演进事件族补全**：plugin_created / tested / promoted / rejected /
   scaffold_retired / restored / ratchet_tightened 全落全局账本——
   **演进系统自己的历史也在账本里**（kernel 详设 §3.5 决策留痕覆盖
   自身）。

### 6.2 演进健康度 KPI

| 指标 | 定义 | 健康方向 |
|---|---|---|
| 任务成功率 | eval 集回归通过率 | 升或平（任何演进不得使其掉点） |
| 自产插件存活率 | auto-* 晋升后 30 天内未被卸载/熔断的比例 | 升（低 = 生成质量差，收敛生成侧） |
| 配对命中率 | 装配的插件实际被调用的比例 | 升（低 = 装配策略差） |
| 回滚率 | promoted → rolled_back 的比例 | 降（高 = 晋升门太松或自测太弱） |
| 脚手架净重 | 应载清单中脚手架数量（按档案加权） | 随模型进步单调降 |
| 权限摩擦 | 每会话 ASK 次数 / 沉淀规则数 | 降（重复摩擦应沉淀为规则） |
| 证据完备率 | 决策事件中带评测/自测证据的比例 | 恒 100%（无证据的决策是 bug） |

## 7. 边界与反模式

### 7.1 这些不叫自演进

| 行为 | 为什么不算 |
|---|---|
| 模型直接改内核 / 棘轮 / 评测门 | TCB 关闭；这是攻破，不是演进 |
| 未经 self_test 的自产插件进会话 | 无证据；信任锚点缺失 |
| 会话内改配置不留账 | 无痕迹；无法归因无法回滚 |
| 为单次任务打的一次性补丁（不沉淀） | 是工具使用，不是演进——演进要求成果进能力库/组合，跨会话存活 |
| 摘除脚手架不做评测 | 无证据；能力棘轮的双向性靠评测门维持 |
| 用户手动装插件 | 是演进系统的正常输入（user 级候选），但发起者是人——系统的"自"体现在感知与生成，不体现在绕过审批 |

### 7.2 主要风险与缓解

| 风险 | 缓解 |
|---|---|
| 能力库膨胀：auto-* 越积越多，目录噪音淹没配对 | 存活率盘点 + 批量回滚；目录只暴露摘要+成本，按使用频率排序（E5） |
| 评测门被"挑题"：eval_set 不覆盖退化场景 | eval_set 属组合输入但修订须用户确认；掉点自动回挂 |
| 策略过拟合：装配建议从历史学到错误的相关 | 建议永远过门；命中率 KPI 持续监测，差则回退到人闭环 |
| 自测 sandbox 逃逸 | 现状 daemon 线程 + 超时是缓解不是证明；D9 进程隔离是既定加固方向，auto 级隔离不可降级 |
| 演进频率失控：模型热衷造插件刷存在感 | 资源闸覆盖装配行为（轮次/预算）；写类变更的用户确认天然限流 |

## 9. 留给评审的决断点

1. **退场评测的审批档位**：评测门通过后，摘除是否仍需用户确认？
   （建议需要——评测覆盖不全的风险由人兜底；档案联动触发的**回挂**
   可自动，收紧方向不审。）
2. **eval_set 的归属**：任务集是组合输入（overlay 可改）还是半 TCB
   （修订须显式审批）？（建议后者——评测门被改写等于门被拆。）
3. **装配策略的在线化时机**：离线报告（人闭环）跑多久、KPI 到什么
   水位才允许模型产 overlay 建议？（建议配对命中率与回滚率连续达标
   后再议，本文不定阈值。）
4. **auto-* 的生命周期**：永久存活 vs 默认带过期（如 90 天未被装配
   自动降级建议卸载）？（建议默认存活 + 定期盘点报告，过期语义引入
   复杂度暂缓。）
5. **经验写入的记忆门**：会话收尾提炼的经验写记忆是否过 ask？
   （建议默认过——记忆是跨会话影响面，静默写入的污染成本高；可配
   档位留给用户。）
