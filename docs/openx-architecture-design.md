# OpenX 架构设计文档 · Like body, not just body

> 定位：OpenX 的总架构。回答一个问题——**harness 如何随模型进步而演进**。
>
---

## 1. 设计目标：会消融的 harness

模型能力在快速增长，harness 的宿命是**变薄**：一切补偿模型短板的模块（压缩、路由、编排、记忆、乃至 loop 本体）终将退场；变重的只有两样——**账本（证据）与把关（信任）**。


> **每个模块必须回答：你补偿的是模型的哪个短板？你的退场条件是什么？**
> 答不出来的，才有资格进内核。

按此判据，内核收缩为四职责：**编排 / 沙箱执行 / 插件维护 / 记账**（2026-08-24 定稿，与原"装配 / 把关 / 记账"机制同构：编排⊃装配，沙箱执行⊃把关）。harness 的终局身份不是 executor，而是 **verifier**——执行能力还给模型，人类信任的锚点留在 harness。

## 2. 六条标准

| # | 标准 | 内容 |
|---|------|------|
| 一 | 内核最小 | 内核只留编排·沙箱执行·插件维护·记账，其余皆可拆 |
| 二 | 安全棘轮 | 只紧不松，任何贡献不可松动安全底线 |
| 三 | 脚手架声明 | 每个脚手架必须声明 compensates 与 exit_when |
| 四 | 服务槽 | 不加载 ≡ 现状，零开销 |
| 五 | 动态组合 | base bundle = f(模型能力档案)，换模型零代码改动 |
| 六 | 插件边界 | 模型只配对、内核才定位；可注册的类型由内核枚举 |

## 3. 五层总览

```
┌─────────────┬─────────────┬─────────────┬────────────┐
│   CLI/TUI   │   DESKTOP   │    WEB      │ 远期:IDE/移动 │  ① 端层（薄）
└──────┬──────┴──────┬──────┴──────┬──────┴────────────┘
       │  渲染事件流 ↓ / 上送意图流 ↑，零 agent 逻辑
┌──────▼─────────────────────────────────────────────┐
│           会话协议层 · openx serve                   │  ② 协议（账本外化）
└──────────────────────┬─────────────────────────────┘
┌──────────────────────▼─────────────────────────────┐
│  微内核 KERNEL:  装配 · 把关 · 记账                   │  ③ 内核（TCB）
└──────────────────────┬─────────────────────────────┘
┌──────────────────────▼─────────────────────────────┐
│  LOOP 核心（第一服务槽）→ Provider/Context/Executor/  │  ④ 循环与零件
│  Tools + 执行槽/协调槽/灰区槽                         │    （全可换）
└────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│  插件层（纵贯四层）：候选池→模型配对→晋升门→激活→记账    │  ⑤ 插件层
└─────────────────────────────────────────────────────┘
```

五层各答一问：端答"人在哪看"；协议答"事件怎么流"；内核答"什么永远不变"；loop 答"今天怎么干活"；插件层答"明天怎么长出新能力"。

## 4. ⓪ 组合输入：模型能力档案

装配的第一输入不是代码，是**模型能力档案**——按模型版本声明能力面：

```yaml
model_profile:
  model: deepseek-v4-flash
  context: 128k
  native_summarization: false
  native_planning: false
  parallel_tool_calls: true
  self_correction: partial
```

- **动态 base bundle**：出厂组合 = `f(档案)` 的计算结果。脚手架以 `requires` / `exit_when` 声明对档案的依赖，loader 据此计算该模型下应挂哪些模块。换模型、模型升级 → 组合自动变化，零代码改动。
- 用户 overlay（`~/.openx/openx.yml`）与项目 overlay（`.openx/openx.yml`）以补丁语义（cordis.patch.yml 式）作用在计算结果上。
- 与协议层的版本协商对称：**一个面向端，一个面向模型**。

## 5. ① 端层：薄客户端

- 端只做两件事：**渲染事件流、上送意图流**。路由、压缩、审批判断出现在任何一端都会导致多端行为分叉——这是不变量。
- CLI/TUI 是参照实现，语义最全但无特权；Desktop 提供系统级能力（剪贴板/截图/全局热键/通知），经意图流上送；Web 提供会话共享、远程批准、复盘回放；IDE/移动是预留位。
- **加端 = 写一个客户端 attach 协议，内核零改动。**

## 6. ② 会话协议层：账本的外化

- **协议 = 账本的外化**：事件流下发的每个事件就是内核记账 append 的账本条目，协议层只是把账本实时广播给挂上来的端。因此回放 = 把存储的事件流再发一遍，复盘回放与实时观看共用同一 schema。
- 双向契约：下行 `text / thinking / tool / permission_request / ui_slot / state` 事件，上行 `message / approve / interrupt / queue` 意图。版本化 + 能力协商；插件扩展走命名空间（`x-*.*`）。
- `openx serve`：会话长存服务端，客户端 attach/detach。关终端 agent 继续跑（tmux 语义）、多端同看一会话、未来长存队友（team 的队友 = serve 管理的子会话）。
- **UI slot 事件族**（`ui_slot_registered / updated / removed`）：插件对界面的修改全部以此为载体，端是哑渲染器——UI 插件对所有端通用，加插件永远不等于客户端发版。

## 7. ③ 微内核：四职责（TCB）

TCB = 微内核自身，不再包含 loop/executor。几百行，小到可独立审计。

### 7.1 装配（工作流串联）

Loader 五阶段照旧：**发现（目录 + entry-points + 动态 base）→ 解析（importlib，失败跳过不炸）→ apply(ctx)（内置失败=致命 / 用户失败=隔离）→ 校验（逐注册验证器，违例拒载）→ 激活（依赖拓扑定序，环=错误）**。

- ctx 给予面：注册 API、服务定位器、logger、只读配置、workspace 信息。
- ctx 拒绝面（同等重要）：loop 与轮次控制、权限闸门绕过、裸 console、他插件私有状态——靠不暴露引用实现，不靠插件自律。
- 注册表即 IPC：插件彼此不认识，loop/executor 也不认识任何具体插件，双方只面对注册表。每条注册带 provenance。
- 新增**会话内动态插入**路径：走同一校验，仅限热插分级允许的注册项类型。

### 7.2 把关（v2 控制平面收编入内核）

- 安全棘轮：只紧不松，force-allow 的 hook 贡献丢弃 + warn。
- 权限裁决：危险永远弹窗、远程批准、manual 默认。
- **资源闸**：停止语义 / 轮次上限 / 预算底线——从原 loop 不变量与预算机制中析出的安全部分，任何 loop 槽实现每轮必过，绕不过。
- 团队安全：权限继承、全队弹窗队列。
- **晋升门**：动态插入的非只读贡献须用户确认，先灰度到当前会话再扩散。
- 把关补偿的是"信任"而非模型能力——**模型再强也不松**。

### 7.3 记账（账本 = 证据系统）

- append-only 事件账本，唯一事实源；协议核心 schema 即账本的外化。
- 可回放、可审计、可归因。
- **决策留痕**：每次进化晋升、脚手架退场、插件插入与回滚，决策本身也记账——将来追问"为什么这个模块没了 / 这个插件哪来的"，答案在账本里。
- 模型越自主，人类越需要事后可验证——这是随模型进步**变重**的一半。

## 8. ④ LOOP 核心与零件层

### 8.1 loop 槽（本架构最大的结构变化）

- v1 的"换循环=换产品"被推翻。**接口形状是内核不变量**：意图进、事件出、工具调用必经执行闸、每轮必过资源闸。**实现进槽**。
- 默认实现 = 现有 harness loop（模型调用 → 工具分发 → 结果回喂，≤30 轮），行为≡现状。
- 预留 **model-native 位**：模型自持循环时，内核退为事件中继 + 闸门 + 记账。协议事件形态从第一天按后者设计，未来切换时多端/回放/审批语义零改动。
- 装配 loop 的机制必须独立于 loop——这是"换 loop 不换产品"的前提，也是内核在 loop 之上的原因。

### 8.2 零件与槽

| 模块 | 归属 | 说明 |
|---|---|---|
| Provider | 零件，可换 | 重试/退避/超时归内核，实现固定 chat/stream 接口 |
| Context | 零件，可换 | 历史 + 组装 + 超限压缩 |
| Executor | 执行槽 | 两阶段骨架（串行审批→并行执行）形状=内核；"工具必须过闸"由把关层强制 |
| Tools | 零件 | 模型的手：内置 + MCP 适配器 + 用户插件的聚合视图 |
| 协调槽 | 服务槽 | Mailbox / TaskBoard / Roster，默认会话式实现 |
| 压缩策略槽 / 审计闸门槽 | 灰区 | 压缩暂不开放；审计闸门倾向开放且只紧不松 |

## 9. ⑤ 插件层（纵贯四层）

**大模型配对 · 微内核定位 · 实时插入。**

### 9.1 插入流水线

```
候选池  →  模型配对  →  内核校验 + 晋升门  →  动态激活 → 分发到层  →  决策记账
```

1. **候选池**：全部预校验 + 签名 + 自描述贡献声明 `contributes=[ui_slot(…)|tool(…)|event(x-*.*)|hook(…)|prompt(…) …]`。三个来源同池：第三方（市场）、用户（本地目录）、模型自产（进化引擎产物）——同源同门，无后门。
2. **模型配对**：模型决定"用哪个插件、建议注册什么"。**可注册的类型由内核枚举，模型不能发明位置**（标准六）——prompt injection 最坏结果是推荐错插件，不能让插件落进内核没开过的口子。
3. **校验 + 晋升门**：形状/越界/只紧不松检查；非只读贡献过用户确认；先灰度到当前会话。
4. **激活分发**：注册表登记；UI slot 经协议下发到端；loop 下一轮即消费。
5. **记账**：谁批准、依据什么、一键回滚 = 卸载。

### 9.2 各层接入点（同一个注册表）

| 层 | 注册项类型 | 说明 |
|---|---|---|
| 端层 | UI slots（面板/行/主题） | 端不跑插件，只渲染协议下发的 slot 声明 |
| 协议层 | 命名空间事件 x-*.* | 插件自定义事件多端可消费 |
| 内核层 | hooks / 策略 / 审计闸 | 只紧不松 |
| 零件层 | tools / prompt 片段 / slash 命令 / providers / 记忆后端 / 协调实现 | loop 经注册表消费 |

### 9.3 热插分级

| 档 | 注册项类型 | 理由 |
|---|---|---|
| 会话内热插 | UI slots · prompt 片段 · tools · 命名空间事件 | 纯加法，回滚=卸载 |
| 会话边界换 | providers · 记忆后端 · 协调实现 | 有状态，热换撕裂引用 |
| 仅 boot 装配 | loop 槽 · 执行槽 · 权限闸 · 账本格式 | 动了就不是同一个产品，也是最大攻击面 |

### 9.4 UI 插件的真实形态

"修改前端界面"不需要碰前端：插件贡献的是协议里的一条 slot 声明 + 渲染规格，端只执行渲染。布局几何受保护：只加面板/行，输入框、主转录区、权限面板是内核领地。

示例：用户说"画出调用关系" → 模型配对 viz 插件（UI slot + 数据工具 + x-viz.* 事件）→ 内核校验只加面板 → 用户确认一次 → 协议下发 ui_slot_registered → CLI/Web/Desktop 同时多出图表面板，三端零代码零发版 → 决策落账可回滚。

## 10. ⑥ 脚手架层与演进机制

### 10.1 脚手架清单（将消融）

| 脚手架 | compensates | exit_when |
|---|---|---|
| harness loop 默认实现 | 模型无自持执行循环 | model-native 循环评测通过 |
| 历史压缩 | 上下文有限 | 长会话免压缩评测通过（预算"存在"仍由资源闸保障） |
| 意图路由 | 模型不自知深浅 | 自规划直连评测通过 |
| 子代理 / workflow / team | 单上下文装不下、单线程不够快 | 原生并行/长任务评测通过 |
| 记忆检索 | 跨会话遗忘 | 持续记忆评测通过 |

**不消融**：内置工具包 / 适配器——模型的手，不补偿短板只演进。

### 10.2 双棘轮

- **安全棘轮**：单向，只紧不松。
- **能力棘轮**：双向，跟随模型实测，以退场评测为证据门（摘除后任务成功率不掉点才准退场；评测是回归测试，模型降级时脚手架自动回挂）。
- 退场三步：评测门 → 决策记账 → 从动态 base 摘除。摘除不是删除。
- TCB 对两者都关闭：进化引擎能产出候选插件、提出退场建议，但棘轮与评测门本身不可贡献。

### 10.3 演进即重组

一切演进都只是改组合输入，内核零改动：

| 演进场景 | 改什么 | 内核 |
|---|---|---|
| 换模型 / 模型升级 | Provider 实现 + 能力档案 | 不改 |
| 模型能自持循环 | loop 槽实现换 model-native | 不改 |
| 加 skill / MCP / memory | 注册表多一条贡献 | 不改 |
| 脚手架退场 | 组合输入删一行 + 退场评测 | 不改 |
| 加一个端 | 写一个客户端 attach 协议 | 不改 |
| 远程批准 / 复盘回放 | 协议已有事件 + 账本重放 | 不改 |
| 会话中途装插件 | 模型配对 + 晋升门 | 不改 |
| 界面随任务生长 | UI slot 动态下发 | 不改 |
| 模型自产进化产物 | 候选插件走同一道门 | 不改 |

## 11. 内核不变量带（七项）

v1 九项收缩至此，全部隶属编排 / 沙箱执行 / 插件维护 / 记账：

1. loader / ctx / 注册表自身（bootstrap 不能是插件）
2. 安全底线（含团队安全语义）
3. 账本格式 + 协议核心 schema
4. 槽接口形状（loop / 执行 / 协调）
5. 资源闸（停止 / 预算 / 轮次底线）
6. 注册项类型枚举（模型只配对，内核才定位）
7. TCB 对动态插入关闭

v1 九项中的 loop 主线、executor 骨架、预算机制、协调接口四项降级：前三者降为槽/脚手架（资源闸析出并入把关），协调接口形状归入槽接口形状不变量。

## 12. 最小内核 + 最小循环（伪代码）

```python
class Kernel:
    def boot(self, composition):                    # ① 装配
        self.registry = load_and_validate(composition)
        self.loop = self.registry.service("loop")        # 绑定 loop 槽

    def gate(self, tool_call):                      # ② 把关
        if not self.approve(tool_call): raise Denied
        if self.turns > self.resource_limit(): raise Budget

    def record(self, event):                        # ③ 记账
        self.ledger.append(event)


class HarnessLoop:                                  # loop 槽默认实现
    def run(self, intent, kernel):                  # kernel 是注入的
        kernel.record(intent)
        for turn in range(kernel.limit):
            resp = kernel.service("provider").chat(kernel.service("context").messages())
            kernel.record(resp)
            if not resp.tool_calls:
                return resp.text
            results = [kernel.gate(t) or execute(t) for t in resp.tool_calls]
            kernel.record(results)
```

## 13. 与当前代码库的映射

| 现有 | 目标归属 | 迁移动作 |
|---|---|---|
| `agent.py`（agentic loop） | loop 槽默认实现 | 移入 `slots/loop.py`，接口形状抽到内核 |
| `permissions.py` | 把关（收编入内核） | 并入 `kernel/guard.py`，析出资源闸 |
| `llm/openai_compat.py` | Provider 零件 | 经注册表注册，重试归内核 |
| `tools/*` | Tools 零件 | 迁入统一注册表，工具表改聚合视图 |
| `ui/console.py` | 端层（协议消费者） | 渲染逻辑与 agent 解耦，等协议层 |
| `main.py`（REPL） | 端层 + 意图归一 | 拆分：输入归一留下，loop 宿主职责交还内核 |
| `sessions/*.jsonl` | 记账（账本） | 升格为证据系统 + 协议事件源 |
| （无） | 内核装配、注册表、槽、协议、插件层 | 全部新增 |

## 14. 落地路线（依赖序）

1. **P1 内核装配**：`kernel/`（loader + ctx + 注册表 + 校验），现有 tools/permissions/llm 迁入注册表——行为≡现状，但组合权已收归内核。
2. **P2 loop 槽化**：agent.py 移入 loop 槽，接口形状入内核；executor 两阶段入执行槽；资源闸析出。
3. **P3 账本 + 协议双向化**：stream-json 升双向，账本格式定版（回放/审计的基础）。
4. **P4 openx serve + Web 端**：会话长存、多端 attach、远程批准、回放。
5. **P5 插件层**：候选池 + 模型配对 + 晋升门 + UI slot 事件族（动态插入）。
6. **P6 能力档案 + 退场评测**：动态 base、双棘轮、脚手架退场机制。

每一步交付后行为都应≡现状（标准四），演进能力逐层打开。
